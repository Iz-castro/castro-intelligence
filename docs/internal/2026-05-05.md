#### 3.5.1. Backend — `increment_usage_metrics` atômico

```python
def increment_usage_metrics(direction, msg_type="", template_category=None, media_size_bytes=0):
    now = utcnow()
    year_month = now.strftime("%Y-%m")
    doc_id = f"usage_{year_month}"
    updates = {"month": year_month, "updated_at": now}
    if direction == "inbound":
        updates["inbound_received"] = firestore.Increment(1)
    elif direction == "outbound":
        if msg_type == "template":
            cat = (template_category or "").strip().lower() or "unknown"
            if cat not in ("marketing", "utility", "authentication"):
                cat = "unknown"
            updates["templates_sent"] = {cat: firestore.Increment(1)}
        else:
            updates["free_form_sent"] = firestore.Increment(1)
    if media_size_bytes and int(media_size_bytes) > 0:
        updates["media_uploaded_bytes"] = firestore.Increment(int(media_size_bytes))
    document("audit_metrics", doc_id).set(updates, merge=True)
```

`firestore.Increment` é resolvido server-side — atomic mesmo sob
concorrência alta (4 webhooks simultâneos do passo 4 do e2e contam 4
exatos). Dispensa o read-modify-write do `increment_audit_metrics`
existente (que mantém `messages_by_half_hour` e por enquanto continua
não-atômico — escopo separado).

#### 3.6.1. Refator — `_fetch_channel_billing_status` extraído

`channel_billing_status` (endpoint `GET /api/wa/channel/{id}/billing-status`)
tinha lógica inline de Graph API. Extraído pra `_fetch_channel_billing_status(channel_id) -> dict`
que retorna dict com `ok=False, error=...` em vez de `raise`. Endpoint
admin chama o helper e converte erros conhecidos
(`channel_not_found`, `missing_waba_id`) em HTTPException; outros
casos retornam o dict cru pra que frontend trate como info de erro.

#### 3.6.2. `_compute_tenant_health` (assume tenant_context)

```python
async def _compute_tenant_health() -> dict:
    channels = get_all_active_channels()
    billing_results = await asyncio.gather(
        *[_fetch_channel_billing_status(ch["id"]) for ch in channels],
        return_exceptions=True,
    )
    # ... classifica payment_method_status, persiste no doc flat de
    # cada canal, agrega per_channel + contadores.
    return {
        "checked_at": ...,
        "channels_total": ...,
        "channels_pending_payment": ...,
        "tokens_expiring_soon": ...,
        "templates_recent_failures": 0,  # placeholder
        "per_channel": [...],
    }
```

`_classify_payment_status(billing, channel)` decide:
- `ok` — `has_payment_method=True`
- `pending` — `has_payment_method=False`, sem outros sinais
- `error` — Graph API falhou (`ok=False`)
- `expired` — coexistence channel cujo `token_expires_at <= now`

`tokens_expiring_soon` conta coexistence channels cujo `token_expires_at`
está entre `now` e `now + 7 days` (warning antes de expirar).

`asyncio.gather(..., return_exceptions=True)` paraleliza Meta calls e
nunca propaga exceção pro nível do cron — cada canal é tratado
isoladamente.

#### 3.6.3. Endpoint `POST /api/internal/cron/health-check`

```python
@app.post("/api/internal/cron/health-check")
async def cron_health_check(request: Request):
    _verify_cron_secret(request)
    for tenant in list_tenants(active_only=True):
        token = set_tenant_context(tenant["id"])
        try:
            health = await _compute_tenant_health()
            fs_doc("health_status", "current").set(health, merge=False)
        finally:
            reset_tenant_context(token)
    return {"checked_at": ..., "tenants_processed": ..., "summary": ...}
```

`_verify_cron_secret` compara header `X-Cron-Secret` com env
`INTERNAL_CRON_SECRET` via `hmac.compare_digest` (timing-safe). Sem env
configurado → 503; mismatch → 401.

Sem auth Firebase porque Cloud Scheduler não tem identidade humana —
quando migrar pra OIDC (com Cloud Scheduler nativamente), header custom
some.

#### 3.6.4. Bug pré-existente em `tenant_service` corrigido

Sintoma: primeira call do passo 9 do e2e retornou `tenants_processed=0`,
mas a chamada manual via curl 1m44s depois retornou `tenants_processed=1`.

Causa: `_last_refresh: float = 0` somado com `time.monotonic()` baixo
no boot (~0.5s no Cloud Run) fazia
`_needs_refresh = (0.5 - 0) > 60 → False`. `_ensure_cache` não chamava
`refresh_tenants` na primeira call → cache permanecia vazio até passar
60s (TTL).

`channel_service` tem o mesmo padrão mas sobrevive porque
`bootstrap_default_channel()` chama `refresh_channels()` explicitamente
no startup. `tenant_service` não tinha bootstrap análogo.

Fix: `_last_refresh: float | None = None` e `_needs_refresh()` trata
`None` como "força refresh". Solução universal — não depende de quem
chama bootstrap.

  explicitamente. `tenant_service` corrigido nesta sessão; outros
  caches (channel/dept) sobrevivem só por bootstrap explícito.
