# Sessão 2026-05-25 — Incidente: 500 em massa ao abrir conversa (hotspot de escrita no audit_log)

> **Atualização 2026-08-21:** o follow-up do §5 (`GET /api/wa/contact/{id}` sem
> escopo por operador) foi **FEITO** em 2026-06-03 — `_require_contact_access` em
> 11 endpoints, commit `cebd367` ([2026-06-03.md](2026-06-03.md) §4).

Incidente de produção investigado a partir do console do Rafal: abrir uma
conversa da equipe na conta admin disparava **500 em vários endpoints ao mesmo
tempo**. Diagnóstico via traceback do Cloud Run, fix em 3 partes, deploy em prod.

**Commit:** `1b0bda6`. **Revisão prod ativa:** `castro-crm-00110-x7m`.

---

## 1. Sintoma

Console do admin ao abrir uma conversa:

```
/api/wa/contact/269   500
/api/wa/contact/245   500
/api/wa/contact/281   500   (e mais: 250, 272, 246, 168)
/api/wa/conversation/2__5531984115898/read   500
```

Front: `div.alert-danger` → `Unexpected token 'I', "Internal S"... is not valid
JSON` (o backend devolveu o corpo de texto `Internal Server Error`, não JSON).

Também apareciam warnings `Cross-Origin-Opener-Policy policy would block the
window.closed call` do `firebase-*.js` — **ruído não relacionado** (polling do
popup de auth do Firebase; tratado em 2026-05-24 com COOP `same-origin-allow-popups`).

## 2. Diagnóstico (traceback real do Cloud Run)

A pista inicial foi que **vários contatos diferentes** falhavam de uma vez (não
era dado de um contato específico) + o `/read` junto. O traceball confirmou que
a causa **não estava** nos handlers de contato/conversa:

```
File "main.py", line 241, in get_current_user
  result = authenticate_firebase_token(token, ip)
File "auth.py", line 132, in authenticate_firebase_token
  log_audit(user["id"], "LOGIN_SUCCESS_FIREBASE", ...)
File "database_firestore.py", line 1886, in log_audit
  audit_id = next_sequence("audit_log")
File "firestore_common.py", line 243, in next_sequence
  ...
google.api_core.exceptions.Aborted: 409 ... cross-transaction contention
ValueError: Failed to commit transaction in 5 attempts.
```

**Causa raiz:** `authenticate_firebase_token` roda em **todo** request autenticado
(dependency `get_current_user` em [main.py](../../main.py)), não só no login, e
gravava `log_audit("LOGIN_SUCCESS_FIREBASE")` a cada chamada. `log_audit` usava
`next_sequence("audit_log")` — transação de incremento num **documento contador
único** (`_meta/counters`). Ao abrir uma conversa, o front dispara uma **rajada de
requests paralelos** (vários `GET /api/wa/contact/{id}` + o `/read`); todos
contendiam pelo mesmo doc → Firestore aborta as concorrentes (`409 Aborted`) →
5 retries → `ValueError` não tratado → **500**. Os endpoints de contato/conversa
eram **vítimas colaterais**: morriam na dependency de auth antes do handler.

É o hotspot de escrita clássico do Firestore (doc único satura ~1 escrita/s
sustentada), amplificado por logar audit em todo request.

## 3. Fix (`1b0bda6`)

1. **[auth.py](../../auth.py) — throttle do login audit.** `LOGIN_SUCCESS_FIREBASE`
   só é registrado **1x por janela de sessão (30 min)** por usuário, via
   `_is_new_login_session(previous_login)` (lê `last_login` antes do
   `update_last_login`). Antes gravava em todo request.
2. **[database_firestore.py](../../database_firestore.py) `log_audit` — remove o
   hotspot.** Usa **doc-id auto-gerado** (`collection("audit_log").document()`) em
   vez de `next_sequence("audit_log")`. O id do audit **nunca** é lido como
   sequencial em lugar nenhum (`get_audit_metrics` usa a coleção `audit_metrics`,
   agregada). Sem o contador único, não há mais transação a contender.
3. **`log_audit` best-effort.** Toda a escrita em `try/except` + `logger.warning` —
   uma falha de auditoria **nunca mais derruba o request** que a originou.

Compatível com o existente: docs antigos de `audit_log` com `id` int continuam
válidos; sem migração de dados. Respeita LGPD (audit de login segue existindo,
só com throttle por sessão).

## 4. Deploy e validação

- `gcloud run deploy castro-crm --source . ...` → rev **`castro-crm-00110-x7m`**,
  100% do tráfego.
- Logs pós-deploy: **0** ocorrências de `Failed to commit transaction` /
  `cross-transaction contention`.
- Validação end-to-end (reabrir conversa na conta admin) feita pelo Rafal — o
  fix é estrutural (hotspot eliminado), não reincide nem sob rajada.

## 5. Notas / follow-ups

- **Padrão a evitar:** não chamar `log_audit`/`next_sequence` por-request em
  caminho quente. `next_sequence` (contador doc único) só para entidades que
  precisam mesmo de id int sequencial **e** sem rajada de escrita.
- Reincide o follow-up de 2026-05-24 (§7): **`GET /api/wa/contact/{id}` não escopa
  por operador** — endpoint apareceu neste incidente; segue valendo escopar por
  segurança (hardening), independente deste fix.
