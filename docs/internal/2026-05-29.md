## 3. Causa-raiz revisada (3 fatores combinados)

O scaling do Cloud Run e nativo (nao tem botao "ligar autoscale"). O
429 sobrevive ao maxScale=40 por 3 gargalos juntos:

1. **Cold start (3-8s) na rampa.** Com `min-instances=0`, depois de
   periodo idle, a 1a request boota uma instance — proximas chegam e
   esperam. O autoscaler nao cria 40 instances de uma vez; sobe em
   degraus. Durante esses degraus, requests intermediarias batem em 429
   "no available instance". `--cpu-boost` ja ativo ajuda mas nao elimina.

2. **State_sync ocupa 1 slot por segundos/minutos, nao milissegundos.**
   `webhook.py:362-369` roda `_process_smb_app_state_sync` via
   `run_in_threadpool` — **a request HTTP fica aberta enquanto o loop de
   ~9000 contatos roda no threadpool**. Com `concurrency=8`, sobram 7
   slots pra resto do mundo (admin, outros webhooks, statuses) no mesmo
   instance, e a CPU=1 vira gargalo. O autoscaler ve "instance ocupada"
   mas hesita em criar outra rapido o suficiente.

3. **Instances pequenas (`cpu=1 mem=1Gi`).** 8 reqs concorrentes + um
   loop pesado de escritas Firestore num unico CPU = GIL + cliente
   Firestore competem. Cada instance "aguenta menos do que deveria"
   antes de saturar.

**Importante: aumentar max-instances alem de 40 NAO resolve.** O serviço
quase certamente nunca chega em 40 instances simultaneas durante o 429
— o problema e **rampa de subida** (cold start + slot longo + instance
pequena), nao **teto**. Confirmar com:

```powershell
# Cloud Run > castro-crm > Metricas > "Instancias de contêiner"
# Olhar pico nas ultimas 24h. Se < 10 → problema NAO e teto.
```

## 4. Opcoes em 3 niveis (do barato pro definitivo)

### Nivel A — Mata cold start (recomendado comecar aqui)

```powershell
gcloud run services update castro-crm `
  --region southamerica-east1 `
  --min-instances=1
```

- **O que faz:** sempre 1 instance quente. 1a request da onda nao espera
  boot. Proximas (2-40) ainda escalam normal, mas em paralelo a 1
  servindo.
- **Custo:** ~$10-15/mes (1 instance idle 24/7 em request-based — no
  modelo de cobranca atual, idle = ~zero, so quente p/ startup).
- **Quando nao basta:** se a onda do state_sync sozinha satura a
  instance quente antes do autoscaler subir as proximas.

### Nivel B — Instance maior (combinar com A se A nao bastar)

```powershell
gcloud run services update castro-crm `
  --region southamerica-east1 `
  --min-instances=1 `
  --cpu=2 `
  --memory=2Gi
```

- **O que faz:** cada instance aguenta 8 reqs + state_sync sem afogar.
  2 CPUs significa que o threadpool do state_sync nao rouba ciclo das
  outras 7 reqs no mesmo instance.
- **Custo:** ~$25-35/mes total (dobra preco por instance ativa, so cobra
  quando ativa em request-based).

### Nivel C — Refactor arquitetural (fix definitivo)

Webhook responde **200 imediato** e enfileira o state_sync em **Cloud
Tasks** (ou Pub/Sub). Worker separado processa.

- **O que faz:** webhook nunca mais segura slot HTTP por minutos. State_sync
  vira job de background com retry nativo. Slot HTTP libera em <100ms.
- **Custo:** ~1-2 dias de refactor + ~$0 de infra (Cloud Tasks free tier
  cobre folgado o volume atual).
- **Quando vale:** se onboardar muitos coex em paralelo (varios syncs
  simultaneos viram regra, nao excecao). Hoje com 3-4 coex ativos, A+B
  cobrem.

### O que NAO ajuda aqui

- **Aumentar max-instances > 40:** so vale se ja bater no teto. Confirmar
  pelo grafico antes.
- **`--no-cpu-throttling` + "Sempre alocada":** muda faturamento pra
  cobranca continua 24/7 (mais caro). Pro design atual do webhook
  (`run_in_threadpool` que espera) **nao traz beneficio** — a request
  fica aberta durante o sync, CPU ja esta alocada nessa janela. So
  vale se fizer o Nivel C.

## 5. Decisao hoje: Nivel B parcial aplicado

Aplicado **CPU=2 + memory=2Gi**. **NAO** aplicado min-instances=1
(deixado pra observacao).

**Quota bateu** ao tentar com `max-instances=40`:
```
CpuAllocPerProjectRegion requested: 80000 allowed: 56000
```
A regiao `southamerica-east1` tem teto de 56.000 mCPU alocaveis pro
projeto. 40 instances x 2 vCPU = 80.000 mCPU → estoura. Solucao:
reduzir max-instances pra 28 (28 x 2 = 56 vCPU, bate exato na quota).

**Comando aplicado:**
```powershell
gcloud run services update castro-crm `
  --region southamerica-east1 `
  --cpu=2 `
  --memory=2Gi `
  --max-instances=28
```

**Config resultante:**
| Setting | Antes | Depois |
|---|---|---|
| CPU | 1 | **2** |
| Memory | 1 GiB | **2 GiB** |
| Max instances | 40 | **28** |
| Min instances | 0 | 0 (inalterado) |
| Concurrency | 8 | 8 (inalterado) |

Capacidade efetiva: 28 x 8 = 224 requests simultaneos sustentados —
folga gigante vs uso real.

**Resultado observado pelo Rafal:** "ja ajudou bastante no ultimo sync".
Sem medicao formal de 429 ainda — confirmar com:
```powershell
gcloud logging read `
  'resource.type="cloud_run_revision" AND resource.labels.service_name="castro-crm" AND httpRequest.status=429' `
  --freshness=2h `
  --format="value(timestamp,httpRequest.requestUrl)"
```

**Por que reduzir de 40 → 28 nao preocupa:** o problema sempre foi rampa
(cold start + slot longo), nao teto. Pico real provavelmente nunca
passou de 10 instances. Se um dia bater no teto, pedir aumento de quota
via Console > IAM & Admin > Quotas > "CPU allocation per project per
region" em southamerica-east1.

## 7. Material de referencia rapido

- **Por que Cloud Run 429 com max=40 livre:** rampa de subida nao e
  instantanea. Autoscaler sobe instances em degraus reagindo a
  saturacao observada. Cold start de 3-8s por nova instance. Requests
  na janela = 429.
- **Por que state_sync e pior que outros webhooks:** segura slot HTTP
  por segundos/minutos (loop de 9000 contatos com writes Firestore),
  enquanto messages/statuses normais terminam em <1s.
- **Onde mexer no codigo se quiser Nivel C:** `webhook.py:362-369`
  (substituir `run_in_threadpool` por enfileirar Cloud Task + responder
  200 imediato). Worker novo consome a task e roda
  `_process_smb_app_state_sync` em background.
