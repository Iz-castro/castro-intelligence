## 2. Otimizacao: reduzir leituras redundantes no Firestore ao trocar de conversa

**Problema:** Ao abrir uma conversa no modo snapshot, o frontend misturava:
- listener de contatos,
- listener de mensagens,
- chamada REST redundante para `/api/wa/messages/{contact_id}`.

Isso gerava leitura duplicada, reabertura desnecessaria de listeners e uso indevido do endpoint de mensagens para marcar conversa como lida.

**O que foi alterado:**
- O listener da lista de contatos passou a ficar **fixo**, sem ser recriado a cada troca de conversa.
- A conversa selecionada passou a ter **apenas um listener dedicado**.
- O endpoint `GET /api/wa/messages/{contact_id}` deixou de marcar mensagens como lidas.
- Foi criado o endpoint explicito `POST /api/wa/contact/{contact_id}/read`.
- O backend agora faz guarda para nao reprocessar leitura se `unread_count` ja estiver zerado.

**Arquivos alterados:**
- `frontend/src/context/CrmContext.tsx`
- `frontend/src/firebase.ts`
- `main.py`
- `database_firestore.py`

## 3. Cache local do Firestore no navegador

**Objetivo:** Melhorar a experiencia ao revisitar conversas e reduzir carga redundante de rede.

**O que foi feito:**
- Ativacao de cache persistente do Firestore usando **IndexedDB** no navegador.
- Inicializacao do Firestore com `persistentLocalCache(...)` e `persistentMultipleTabManager()`.

**Resultado esperado:**
- Conversas recentemente abertas podem aparecer imediatamente a partir do cache local.
- O SDK continua sincronizando com o servidor, mas a UX fica mais rapida e estavel.

**Arquivo alterado:** `frontend/src/firebase.ts`

## 4. Protecao contra clique nervoso na troca de conversas

**Problema:** Um usuario poderia alternar rapidamente entre muitas conversas e forcar varias aberturas de query quase sem necessidade.

**O que foi implementado:**
- **Debounce de abertura da conversa**: o listener da conversa so abre apos ~350ms.
- **Cache em memoria das conversas recentes**: ate 12 conversas ficam reaproveitaveis instantaneamente no frontend.
- **Debounce de leitura**: o `POST /read` so dispara apos ~1.2s com a conversa ainda aberta.
- Se o usuario sair rapido da conversa, o timer e cancelado e o request nao ocorre.

**Resultado observado em teste manual:**
- O `Network` passou a mostrar **2 requests/streams principais**:
  - 1 da lista de contatos
  - 1 da conversa ativa
- Ao trocar muito rapido entre conversas, novas requisicoes deixam de ser abertas.

**Arquivo alterado:** `frontend/src/context/CrmContext.tsx`

## 5. Correcoes no fluxo de resposta de mensagens: CRM x WhatsApp

**Problema encontrado:** A feature de resposta de mensagem funcionava visualmente no CRM, mas **nao aparecia como resposta real no WhatsApp**. A citação estava sendo salva internamente no CRM, porem nao era enviada para a Meta com o contexto da mensagem original.

**Causa tecnica:**
- O backend persistia `reply_to_message_id`, `reply_to_preview` e `reply_to_sender_name`.
- Porem o envio outbound para a Cloud API **nao enviava `context.message_id`**.
- No inbound, o webhook tambem **nao resolvia `msg.context.id`** para vincular a resposta recebida do cliente a uma mensagem existente no banco.

**O que foi implementado:**
- Novo helper para montar o contexto de resposta outbound com base no `wa_message_id` da mensagem original.
- Mensagens de texto, localizacao, midia e audio agora enviam `context.message_id` para a Meta quando forem respostas.
- O webhook inbound agora le `msg.context.id`, procura a mensagem original localmente por `wa_message_id` e popula:
  - `reply_to_message_id`
  - `reply_to_preview`
  - `reply_to_sender_name`

**Resultado esperado:**
- Quando o atendente responde uma mensagem no CRM, o cliente ve no WhatsApp qual mensagem foi respondida.
- Quando o cliente responde no WhatsApp uma mensagem da empresa, o atendente ve no CRM a bolha com a citação correta.

**Arquivos alterados:**
- `main.py`
- `media.py`
- `webhook.py`
- `database_firestore.py`

## 7. Feature: identidade visual por operador na aba Equipe

**Objetivo:** Dar visibilidade rapida para o gerente identificar quem esta falando com cada cliente na aba `Equipe`, sem depender apenas do filtro por operador.

**O que foi implementado:**
- Criada uma faixa de bolinhas no topo da coluna de conversas, ao lado de `Equipe`, com a inicial do login do operador.
- Cada operador recebe uma cor propria e consistente.
- Ao passar o mouse sobre a bolinha, aparece o nome do operador.
- Cada conversa da lista da aba `Equipe` passou a exibir o mesmo acento visual da cor do operador responsavel.
- As mensagens outbound dentro da conversa tambem passaram a usar o mesmo destaque visual do operador.
- O filtro existente por operador no dropdown foi mantido sem alteracoes de comportamento.

**Detalhes tecnicos:**
- O endpoint `/api/operators` passou a devolver tambem o campo `username`.
- O frontend passou a usar `operator_id` e `username` para gerar a cor e a inicial de cada operador.
- A normalizacao das mensagens foi ajustada para preservar `operator_id` no snapshot.

**Arquivos alterados:**
- `frontend/src/App.tsx`
- `frontend/src/styles.css`
- `frontend/src/types.ts`
- `frontend/src/utils/normalization.ts`
- `main.py`

## 8. Documentacao: fluxo de deploy por imagem Docker no GCP

**Objetivo:** Registrar um fluxo mais rapido e mais controlado de deploy no Cloud Run, usando imagem pronta em vez de `--source .`.

**O que foi documentado em `docs/deploy-gcp.md`:**
- Como autenticar o Docker no Artifact Registry.
- Como buildar a imagem localmente com `docker build`.
- Como publicar a imagem com `docker push`.
- Como fazer deploy com `gcloud run deploy --image`.
- Diferenca pratica entre:
  - `gcloud run deploy --source .`
  - `docker build` + `docker push` + `gcloud run deploy --image`
- Observacao de que `gcloud builds submit` ainda faz o build na nuvem, nao no computador local.

**Arquivo alterado:** `docs/deploy-gcp.md`
