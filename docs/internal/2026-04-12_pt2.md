## 2. bot_key estavel para roteamento do bot

### Problema

`bot_service.py` tinha `_SETOR_NOMES = {1: "Comercial", 2: "Financeiro", 3: "Administrativo", 4: "SAC"}` hardcoded e o mapeamento `setor -> department_id` usava substring match contra o nome do departamento. Se admin renomeasse "Vendas" para "Comercial - Loja SP", o match quebrava silenciosamente. Alem disso o cache `_dept_cache` nunca era invalidado apos CRUD de departamento.

### Solucao

Adicionado campo `bot_key` em `departments` com valores `comercial | financeiro | administrativo | sac | null`:

- `database_firestore.py` - `create_department`/`update_department` aceitam `bot_key`; `_normalize_bot_key` valida contra whitelist; `_SENTINEL` usado em `update_department` para distinguir "nao enviado" de "limpar".
- `bot_service.py:_get_dept_map()` - 2 passadas: primeiro `bot_key` (prioridade), depois substring como fallback para retrocompat.
- `main.py` - endpoints POST/PUT/DELETE de departments passam `bot_key` ao DB e chamam `invalidate_dept_cache()` (lazy import).
- `bootstrap_data.py` - defaults ja saem com `bot_key`: Vendas→comercial, Suporte→sac, Financeiro→financeiro, Geral→null.
- `frontend/src/types.ts` - tipo `BotKey` + campo `bot_key` em `Department`.
- `frontend/src/App.tsx` - select "Setor do bot" no form de criar/editar departamento + chip visual na lista.

### Benefico colateral

O bug "cache nunca invalidado" (que ja existia antes do `bot_key`) foi corrigido junto. Qualquer mutacao de departamento agora zera o cache.

## 4. Bug: bot roteou para SAC mas apareceu em "Novos" para operadores de todos os setores

### Causa

O filtro de `novosContacts` em `CrmContext.tsx` nao olhava `department_id`. Qualquer operador via qualquer contato sem atribuicao, mesmo com department_id preenchido pelo bot.

### Fix

Linha 376-384 de `CrmContext.tsx`:
```ts
if (!isManagerRole && c.department_id != null && c.department_id !== sessionUser?.department_id) return false;
```

Operador comum so ve contatos do proprio setor (ou sem setor). Admin/supervisor continuam vendo tudo.

### Observacao importante

Contatos que **ja estavam** em "Novos" com `department_id=null` (porque o bot finalizou antes de os `bot_key` estarem setados) nao migram sozinhos. So novos contatos a partir dessa revisao tem roteamento correto.

## 5. Setor no TopBar

### Armadilha

Sessao antiga nao tem `department_name`. Usuario precisa relogar para o backend buscar enriquecido. So novos logins ja carregam.

## 6. Scroll da coluna de contatos (terceira iteracao)

### Causa 1 - media query matava altura fixa

`@media (max-width: 1200px)` em `styles.css:1182-1195` setava `.crm-layout { height: auto }`, `.crm-grid { height: auto }` e `.panel { height: auto }`. Com `height: auto`, o `flex: 1 1 0` + `min-height: 0` dos containers internos perdia a referencia de altura fixa e eles cresciam com o conteudo em vez de scrollar.

**Fix**: breakpoint 1200 removido. Layout desktop de 4 colunas com scroll interno agora funciona ate 861px. Abaixo disso, ainda ha o breakpoint 860 com layout mobile (1 coluna, scroll de documento).

### Causa 2 - cadeia de height nao fechava

Mesmo com o 1200 removido, o scroll ainda nao aparecia em algumas viewports porque grid items com `align-self: stretch` + `min-height: 0` podem nao receber altura definite de forma consistente.

**Fix**: adicionado `height: 100%` explicito em `.panel` (`styles.css:228-233`).

### Causa 3 - cards individuais podem estourar

Mesmo com coluna scrollavel, um unico card (ex: "Usuarios e Roles" com muitos operadores) pode ficar gigante e empurrar os outros para fora da area visivel.

**Fix**: adicionado `max-height: 40vh; overflow-y: auto` em `.collapsible-body` (`styles.css:1008-1014`). Agora cada card tem scroll proprio quando seu conteudo ultrapassa 40% da viewport.

### Resultado final

Dois niveis de scroll:
1. Externo no `.panel.detail-panel` quando a soma dos cards ultrapassa a altura.
2. Interno em cada `.collapsible-body` quando um card passa de 40vh.
