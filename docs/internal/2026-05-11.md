## 1. Diagnostico — por que so 50 contatos sem conversas reais aparecem?

Rafa abriu o CRM pela manha e percebeu que a sidebar mostrava 50
"conversas" todas com data `11/05 12:51` e nenhuma das 5 conversas
reais do history sync (Rafael, Cleide, Tamiris, Facebook Business,
WhatsApp Business).

Inspecao do Firestore prod revelou:

```
TOTAIS: 160 contatos, 160 conversations, 56 mensagens
Conversations COM mensagens: 5
Conversations VAZIAS (criadas por smb_app_state_sync): 155
```

**Causa-raiz tripla:**

1. **`upsert_wa_contact` cascateia em `upsert_wa_conversation`** — toda
   vez que um contato e criado ou atualizado, ja cria a conversation
   correspondente. Pra mensagens reais isso e correto; pra
   `smb_app_state_sync` (que sincroniza contatos da agenda telefonica)
   gera lixo.

2. **`upsert_wa_contact` seta `last_message_at = now` mesmo no
   state_sync** — os 155 contatos da agenda ganharam timestamp de
   ~12:51 (hora da sincronizacao).

3. **Snapshot do frontend usa `orderBy("last_message_at", "desc") +
   limit(50)`** — pegou os 50 mais "recentes" = os 50 do state_sync.
   As 5 com mensagens reais (com `last_message_at` de janeiro/fev/etc)
   ficaram fora da janela.

Plus: busca local depende de `contactsById.get(conv.contact_id)`. Se
o contato nao esta no snapshot de 50, a busca tambem nao acha.

## 7. Race condition do auto-select — fix com insercao otimista

Primeira vez clicando em contato: funcionava. Segunda vez: modal
fechava e voltava pra conversa anterior, **sem abrir a nova**.

Logs Cloud Run confirmavam: 3 chamadas `POST /conversation/open`
todas com `200 OK`. Backend estava OK.

Causa em [CrmContext.tsx:700-708](../../frontend/src/context/CrmContext.tsx#L700-L708):

```ts
useEffect(() => {
    if (!conversations.length) {
      if (selectedThreadId) setSelectedThreadId(null);
      return;
    }
    if (!selectedThreadId || !conversations.some((c) => c.id === selectedThreadId)) {
      setSelectedThreadId(conversations[0].id);
    }
}, [conversations, selectedThreadId]);
```

Race:
1. Frontend chama API → backend cria conv → frontend chama
   `setSelectedThreadId(newId)`.
2. **Snapshot Firestore ainda nao propagou** a nova conv ate o estado
   local `conversations`.
3. Effect ve `selectedThreadId = newId` mas `conversations.some(...) ==
   false` → executa `setSelectedThreadId(conversations[0].id)`.
4. Resultado: selecao volta pra primeira conv existente. UI parece
   "nao fez nada".

Quando funcionava (1a vez): snapshot foi rapido o suficiente — race
ganhou. Quando nao: race perdeu.

**Fix:** insercao otimista. Antes do `setSelectedThreadId`, o
`openConversationForContact` insere a conversation no estado local
(normalizada com dados conhecidos: id, contact_id, channel_id,
assigned_to=current_user). Quando o effect roda, `conversations.some`
retorna `true` e nao rebatiza. Quando o snapshot real chegar depois,
sobrescreve com versao completa (idempotente).

```ts
setConversations((prev) => {
  if (prev.some((c) => c.id === res.conversation_id)) return prev;
  const optimistic = normalizeConversation({
    id: res.conversation_id,
    contact_id: res.contact_id,
    channel_id: res.channel_id,
    assigned_to: sessionUser?.id ?? null,
    assigned_to_uid: sessionUser?.firebase_uid ?? "",
    status: "open",
    unread_count: 0,
  }, res.conversation_id);
  return [optimistic, ...prev];
});
setSelectedThreadId(res.conversation_id);
```

## 8. Cache em memoria do contact picker (LGPD-safe)

Rafa relatou: cada clique no icone de agenda demora pra abrir a lista
(fetch backend). Pediu cache, mas se preocupou com LGPD.

Solucao escolhida: **state do React no `CrmContext`** —
`allContactsCache: Contact[] | null`. Caracteristicas:

- **Sem `localStorage`/`IndexedDB`**: zero persistencia em disco.
- **Vive enquanto provider esta montado**: zera com refresh da pagina,
  logout, ou aba fechada.
- **Pre-aquecido automaticamente**: o effect do `ContactList` ja chama
  `loadAllContacts()` no mount pra mostrar "160 contatos cadastrados".
  Quando user clica no icone depois, modal abre instantaneo.
- **Busca filtra local**: nao bate API em cada keystroke. Mais rapido
  ainda que antes (que tinha debounce 250ms + request).
- **Invalidado em `createManualContact`**: novo contato aparece no
  proximo open do modal.

```ts
async function loadAllContacts(q?: string) {
  let cache = allContactsCache;
  if (!cache) {
    const res = await getJson(...);
    cache = res.contacts.map(normalizeContact);
    setAllContactsCache(cache);
  }
  if (q?.trim()) {
    const needle = q.trim().toLowerCase();
    return { contacts: cache.filter(matches(needle)), total: cache.length };
  }
  return { contacts: cache, total: cache.length };
}

async function refreshAllContacts() {
  setAllContactsCache(null);  // forca reload na proxima
}
```

Aderencia LGPD: dados pessoais (nome, telefone) ficam apenas em RAM
durante a sessao ativa do operador autenticado. Mesma garantia que
ja temos pra `contacts`/`conversations`/`messages` do CRM em si.

## 10. Aprendizados

### 10.1 Funcoes "core" nao devem cascatear side-effects opcionais

`upsert_wa_contact` cascatear em `upsert_wa_conversation` parecia OK
ate aparecer um caso de uso (state_sync) onde so o contato faz
sentido. **Side-effects implicitos viraram poluicao quando o caller
nao esperava**. Adicionar flag explicita (`from_message_event`) e
default conservador (mantem comportamento antigo) e o caminho.

### 10.2 Snapshot Firestore tem latencia perceptivel — usar insercao otimista quando seleciona algo recem-criado

POST cria doc → response chega → mas o `onSnapshot` listener ainda
nao propagou. Race entre setSelectedXXX e effects que validam contra
a lista local. **Insercao otimista** resolve sem precisar mexer no
effect (que nao conhece o context da intencao do user).

### 10.3 Cache em memoria do provider e LGPD-safe e tem perf otima

Sem persistencia em disco, dados vivem apenas durante a sessao
autenticada. Pre-aquecimento via effect de UI ja existente custa zero
extra (a chamada ja acontecia pro contador) e deixa a UX instantanea.
Padrao reutilizavel pra outras listas pesadas.

### 10.4 Snapshot listener nao remove ordens stale automaticamente

Quando uma colecao perde docs (155 conversations deletadas no
backfill), o `onSnapshot` propaga corretamente — o array `snap.docs`
ja vem sem elas. Mas o **state local** dos componentes precisa ser
substituido inteiro (`setConversations(next)`, nao merge). O codigo
ja fazia isso, mas vale anotar.
