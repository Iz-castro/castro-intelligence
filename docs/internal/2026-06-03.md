## 1. Incidente: prod degradada (500/503/429 no /webhook)

**Sintoma:** enxurrada de `500`/`503`/`429` concentrados no `/webhook`.

**Causa raiz:** `FEATURE_AUDIO_TRANSCRIPTION=true` fazia cada instancia em
cold-start **baixar o modelo `faster-whisper-base` do HuggingFace em runtime**,
dentro do startup event do FastAPI ([main.py](../../main.py) ->
`transcription_service.init_speech_client` -> `WhisperModel("base")`). O
download (lento, sem `HF_TOKEN`, rate-limited) **bloqueava o bind na porta 8080**
-> startup TCP probe estourava (`DEADLINE_EXCEEDED`) -> "instance was not
started" -> com `minScale=0` e pico no webhook, Cloud Run nao subia instancia
saudavel -> "no available instance". A Meta re-tentava webhooks com erro,
amplificando (loop).

**Mitigacao (rev 00129):** `gcloud run services update castro-crm
--update-env-vars FEATURE_AUDIO_TRANSCRIPTION=false` — instancias voltam a subir
em segundos.

**Fix definitivo (commit `1b71ef0`, rev 00130/00131):** modelo **embutido na
imagem** no [Dockerfile](../../Dockerfile): `ARG WHISPER_MODEL_SIZE=base`,
`ENV HF_HOME=/opt/hf-cache`, `RUN python -c "from faster_whisper import
WhisperModel; WhisperModel('base', device='cpu', compute_type='int8')"`, e
`ENV HF_HUB_OFFLINE=1` (runtime nunca toca a rede do HF). Flag religada;
log confirma `Faster Whisper carregado | modelo=base` + probe na 1a tentativa
+ zero `huggingface.co`. **Mudar `WHISPER_MODEL_SIZE` passa a exigir rebuild.**

**Aprendizado:** ligar a transcricao sem o modelo na imagem derruba prod. Ver
ADR/risco registrado.

## 2. Feature: reabertura automatica de atendimento

**Pedido:** o template de inatividade (nome real na Meta: **`atualizao_de_solicitao`**
— a Meta removeu os acentos de "atualizacao de solicitacao") exigia o operador
digitar `{{1}}` e `{{2}}` manualmente. Automatizar + registrar a resposta do
cliente (Retomar/Encerrar).

**Backend:**
- Novo `POST /api/wa/conversation/{id}/reopen` ([main.py](../../main.py)):
  `{{1}}` = primeiro nome (`whatsapp_profile_name`->fallbacks), `{{2}}` = data da
  ultima conversa (`conversation.last_message_at` em **DD/MM/AAAA BRT** — sem
  query/protocolo extra). Reusa `/api/wa/send-template` (guard WABA + billing).
  Nome/idioma do template vem do frontend (ou env `REOPEN_TEMPLATE_NAME`).
- [webhook.py](../../webhook.py) passou a tratar `msg_type == "button"` (antes
  caia no `else` como `[button]`, no-op): resolve a conversa via `context.id`,
  grava `reopen_response` + mensagem de sistema visivel ao operador, e
  curto-circuita bot/rating/takeover.
  - **Encerrar chamado** -> `attendance_status="fechado_cliente"`,
    `client_requested_close=true` (trava p/ reabertura em lote futura), fecha o
    Atendimento diario e **envia o recibo de protocolo** (mesma logica do
    fechamento manual, `_close_daily_and_send_protocol`).
  - **Retomar solicitacao** -> reabre (`aberto`) + reabre Atendimento diario.

**Frontend:** `TemplatePickerModal` ([App.tsx](../../frontend/src/App.tsx))
detecta o template de reabertura **pelos botoes quick-reply** (Retomar/Encerrar)
— robusto a variacoes de nome — e auto-preenche `{{1}}/{{2}}` (sem caixa manual);
botao "Enviar reabertura" chama o novo endpoint. Selo "fechado (cliente)".
`reopenConversation` no [CrmContext.tsx](../../frontend/src/context/CrmContext.tsx).

> Pegadinha que custou um deploy: eu casava o template pelo nome `atualizacao_solicitacao`,
> mas o nome real (Meta sem acentos) e `atualizao_de_solicitao`. Achei o nome real
> nos logs (`WA_SEND_TEMPLATE template=...`). Solucao: detectar pelos botoes (commit `2d64ff2`).

## 3. LGPD: vazamento de isolamento entre operadores (departamento)

**Relato (Rafa):** ao cadastrar o coexistence da danielle, **todos os contatos
da aline apareciam na agenda da danielle** (conversas nao; contatos sim).

**Causa raiz (confirmada com dados de prod):** o escopo do operador comum incluia
`where department_id == <meu depto>`, presente em **3 camadas**. Como a agenda
coexistence (sincronizada do celular via `smb_app_state_sync`) e toda atribuida
ao dono mas tem `department_id` do depto, qualquer colega do mesmo departamento
via a agenda pessoal do outro. aline (id 7) e danielle (id 16) ambas no dept 2;
aline tinha 175 contatos. No dept 5 (almoxarifado), joaobosco (474 contatos) era
visto por fernanda/evandro/frederico. **0 orfaos** (nao era pool — era depto).

**Fix (commits `ddcfb69`, `e2cecf8`):** removida a clausula de departamento de:
- backend `get_wa_contacts_scoped_for_user` ([database_firestore.py](../../database_firestore.py))
- frontend `buildContactSnapshotTargets` + `buildConversationSnapshotTargets`
- `firestore.rules` `canSeeContactScoped` (subcolecao + flat legada); funcao
  morta `canSeeConversation` removida.

Modelo atual: **operador comum ve SO o atribuido a si + o pool sem dono
(`assigned_to_uid` vazio)**; admin/supervisor veem tudo.

**Verificacao:** rodei a funcao corrigida contra prod simulando a danielle ->
**0 contatos da aline** (era 175). Confirmado tambem manualmente pelo Rafa no
CRM. Rules publicadas pelo Rafa **no console** (firebase CLI nao instalado nesta
maquina; a conta gcloud nao tem permissao de leitura na Firebase Rules API — 403).

## 4. Auditoria adversarial (workflow) -> gate REST

Rodei um workflow multi-agente auditando o isolamento. Resultado: o vazamento
por departamento era **1 instancia de um padrao maior** — varios endpoints REST
escopavam so por *tenant*, nao por operador (`get_current_user` so autentica;
ids sequenciais enumeraveis; o Admin SDK do backend ignora as Firestore rules).
**22 achados confirmados** (reais + alcancaveis por operador comum).

**Fix (commit `cebd367`, rev 00135):** helper `_require_contact_access(contact,
current_user)` (admin/supervisor tudo; operador comum so contato proprio ou pool
-> 403) aplicado em **11 endpoints**: `GET /api/wa/messages/{contact_id}`,
`POST /messages/{id}/transcribe`, `GET /api/wa/conversations` (operador comum
passou a usar `get_wa_contacts_visible_to`), `GET /api/wa/contact/{id}`,
`PUT .../qualify`, `PUT .../declared-name`, `POST .../read`, `DELETE` + `restore`,
`GET /api/wa/transfer-history/{id}`. Confirmado em prod: `/api/wa/contact/{id}`
retorna 200/403 misto (gate barrando cross-operador), sem 500.

**Pendente (proximo round):**
- `wa_messages` rules: o app le mensagens via **Web SDK** (snapshot por
  `conversation_id`), entao a rule `firestore.rules` (`ownsTenant`) deixa
  qualquer operador ler TODAS as mensagens via query direta. Fix exige
  **denormalizar `assigned_to_uid` nos docs de mensagem + backfill + atualizar no
  transfer**.
- negar colecoes legadas (`wa_messages` flat, `messages` internas);
- Google Chat por participante (feature ainda nao usada);
- fix do **write-path** do history sync (conversa herdar o dono do contato).

## 5. Incidente de capacidade (429)

Durante a investigacao, a carga combinada (admin carregando todas as ~1.359
conversas + ~7.061 contatos no snapshot, repetidas vezes; meus diagnosticos
varrendo o Firestore; cliques nos 361 leads) **estourou o teto de 28 instancias**
-> `/webhook` deu 429 -> Meta re-tentou -> "incontaveis 429 por nao ter instancia
disponivel" (mesmo loop do incidente do Whisper).

**Mitigacao:** `gcloud run services update castro-crm --max-instances 80
--min-instances 3` (rev 00136) -> 429 cessaram, webhook voltou a 200.

**Dialback (rev 00137):** `max-instances=40, min-instances=0` (era 28/0). Com o
modelo Whisper embutido, cold-start e rapido, entao `min=0` nao tem desvantagem.

**Contribuintes a endurecer:** o frontend nao faz backoff em erro repetido
(storm de retry) e o snapshot do admin e ilimitado (le tudo) — ambos amplificam
picos. (Pendente.)

## 6. Backfill: 361 conversas orfas de dono

**Achado:** 361 conversas (todas coexistence, do canal 2 "removido/antigo") com
`assigned_to_uid` vazio mas **contato com dono** (gerencia 356, jaqueline 4,
joaobosco 1) — descasamento contato↔conversa (provavelmente do history sync, que
atribui o contato mas nao a conversa). Conversa sem dono = **fila global "Novos"**,
visivel a todos -> poluia a caixa do admin (e seria vista por operadores via o
pool). Nao era o vazamento por departamento; nao foi causado pelas mudancas de hoje.

**Backfill aplicado (script ad-hoc, com dry-run antes):** cada conversa orfa cujo
contato tem dono herdou `assigned_to` + `assigned_to_uid` (+ `department_id`) do
contato. **361 atualizadas** -> sairam de "Novos" pro bucket do dono. Idempotente.

> Obs: o "22 vs 361" que apareceu na tela do admin era o snapshot carregando
> progressivamente (22 parcial -> 361 total). Sem misterio.

## 8. Aprendizados de deploy/infra (importante)

- **NAO usar `deploy.ps1`/`deploy.sh`** — desatualizados; clobberam env/secrets/
  scaling de prod (perderiam `META_APP_SECRET`, `FEATURE_GOOGLE_CHAT`,
  `CRON_OIDC_*`, e reduziriam scaling). Deploy correto: `gcloud run deploy
  castro-crm --source <CAMINHO ABSOLUTO DA RAIZ>` (preserva config) ou
  `gcloud builds submit <raiz absoluta> --tag <AR>/castro-crm:TAG` + `gcloud run
  deploy --image`.
- **Sempre passar caminho absoluto** como source. O `.` quebrou 2x porque o
  working dir do shell tinha ficado em `frontend/` (apos `npm run build`) ->
  `gcloud --source .` foi pra Buildpacks (EACCES `/frontend_dist`) e
  `builds submit . --tag` deu "Dockerfile required".
- **`CLOUDSDK_PYTHON`** tem que apontar pro Python312 (senao pega 3.8).
- **firebase CLI nao instalado** nesta maquina -> Firestore rules publicadas
  **pelo console** (copiar `firestore.rules` inteiro). A conta gcloud nao tem
  permissao de leitura na Firebase Rules API (403 ao verificar via REST).
