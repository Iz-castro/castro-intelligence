## 2. Coex self-signup por operador (item 1) — `242ed3e`

**Problema:** o Embedded Signup só era permitido a admin/supervisor, e o **owner
do canal coex = quem está logado** (`main.py` `embedded_signup_exchange`:
`owner_id = body.owner_user_id or current_user["id"]`; o frontend não passa
`owner_user_id`). Logo, não havia caminho limpo pro operador comum ter o próprio
número com `owner = ele` sem promover/rebaixar.

**Solução (fluxo aprovado pelo Rafal):** o admin/supervisor **pré-autoriza** o
número na linha do usuário (botão **"Coex"**), e o **próprio operador** faz o
Embedded Signup, virando owner.

**Backend (`main.py`, `database_firestore.py`):**
- Campos novos no user: `coex_authorized` (0/1), `coex_phone` (só dígitos).
  `set_coex_authorization()`; `get_user_by_id`/`create_user`/`_sync_operator_profile`
  carregam os campos; `/api/session` e `/api/operators` expõem.
- `POST`/`DELETE /api/admin/users/{id}/coex` (admin/supervisor; audit
  `COEX_AUTHORIZE`/`COEX_REVOKE`, loga só os 4 últimos dígitos).
- Gate do signup (`/config` e `/exchange`) aceita operador com `coex_authorized`.
  **Trava de segurança:** operador não-privilegiado sempre vira `owner=self`
  (ignora `owner_user_id` do body) e só cria canal coex (não standard).
  **Validação:** o número conectado tem que bater com `coex_phone`
  (`normalize_br_phone`, 9º dígito), senão **422**.

**Frontend (`App.tsx`, `CrmContext.tsx`, `types.ts`):** botão "Coex" + edição
inline na linha do usuário (estilo `admin-user-edit`); `saveCoex`/`revokeCoex`
(recarrega operators p/ refletir o chip "📱 Coex"); tela "WhatsApp Coexistence"
liberada pro operador autorizado.

## 3. Filtro da agenda Meus / UserN / Todos (item 2)

Barra de botões no topo do `NewContactModal` (só admin/supervisor) filtrando por
**`assigned_to`** (carteira), **client-side** sobre o cache já carregado — **zero
leitura nova no Firestore**.

Decisão importante: usar `assigned_to` e **não** `created_by_user_id`. Confirmado
no código que `created_by_user_id` é **`None`** pra tudo que vem de webhook/
state_sync ([database_firestore.py:797](../../database_firestore.py#L797)) — só
preenchido em cadastro manual. Como "coex do meu número" tem creator nulo,
filtrar por creator deixaria ~toda a agenda de fora; `assigned_to` (dono/carteira)
captura "o que criei + coex do meu número". Custo: full-scan do admin (~6k docs)
≈ centavos; com cache + single-flight, ~1 scan por sessão.

## 6. Takeover temporário (Fases 1 e 2) — `242ed3e` + `1c8cdc9`

**Problema de negócio:** no coex multi-operador cada operador tem SEU número. Um
cliente que é lead do operador X pode mandar pro número do operador Y. Y precisa
poder atender a urgência **sem roubar a posse do lead** de X.

**Nuance do coex:** o número é **físico** do Y. "Devolver pro X" não reroteia (o
cliente continua mandando no número do Y) — só encerra a sessão e registra; novas
mensagens nesse canal reabrem `pending`.

**Modelo (campos novos na `wa_conversation`):** `takeover_status`
(none|pending|active), `lead_owner_user_id` (X), `takeover_handler_user_id`
(Y = `channel.owner_user_id`), `takeover_started_at`.

### Fase 1 (`242ed3e`)
- **Detecção** em `webhook.py` `_process_messages` (após o log `[WA IN]`): canal
  coex + `contact.assigned_to` existe e ≠ `channel.owner_user_id` →
  `flag_conversation_takeover` marca `pending`. Cliente novo (sem dono) não gera
  conflito. Só roda em mensagens **novas**.
- `database_firestore.py`: `flag_conversation_takeover` (idempotente, não reverte
  `active`), `set_conversation_takeover_active`, `clear_conversation_takeover`.
- `main.py`: `POST /api/wa/conversation/{id}/takeover` e `/return` (+ system
  message + audit `TAKEOVER_START`/`TAKEOVER_RETURN`). `_check_conv_send_permission`
  recusa envio durante `pending`.
- **Frontend:** banner + bloqueio do composer + botões; **lazy-fetch** do contato
  fora do snapshot escopado (`CrmContext` `extraContacts` + efeito que busca
  `GET /api/wa/contact/{id}` pros contact_ids de conversas do operador ausentes —
  resolve o "conversa some" da Descoberta B).

### Fase 2 (`1c8cdc9`)
- **Mensagem ao assumir (opcional/editável, menciona o dono X):** o botão
  "Assumir" abre um textarea com saudação sugerida → "Assumir e enviar" / "sem
  mensagem". `takeoverConversation(id, greetMessage?)` faz `/takeover` e, se
  houver msg, `POST /api/wa/send` (respeita janela 24h; fechada = avisa).
- **Timeout (inatividade total):** `config.TAKEOVER_TIMEOUT_HOURS` (env, default
  **3**); `expire_stale_takeovers()` devolve sessões `active` com `last_message_at`
  > 3h → `none` + system msg + audit `TAKEOVER_AUTO_RETURN`; endpoint
  `POST /api/internal/cron/expire-takeovers` (mesma auth `_verify_cron_auth` do
  health-check).

### Cloud Scheduler de prod (2026-05-24)
Primeiro cron de **prod** (antes só staging tinha). Como o endpoint já estava
deployado (rev `00108`), bastou habilitar a auth OIDC:
- `gcloud run services update castro-crm` com `CRON_OIDC_AUDIENCE` (= URL do
  endpoint) + `CRON_OIDC_SERVICE_ACCOUNT` → rev `00109-w6n`.
- `roles/run.invoker` à SA `castro-crm-scheduler` no `castro-crm`.
- Job `castro-crm-expire-takeovers` (southamerica-east1, `*/30 * * * *`,
  America/Sao_Paulo, OIDC). **Validado:** disparo manual e automático retornaram
  **200**.
- ⚠️ Prod usa **só OIDC** (sem `INTERNAL_CRON_SECRET`); o backend valida `aud ==
  CRON_OIDC_AUDIENCE` (exato). Um 2º job cron em prod precisa usar a **mesma
  audience** ou um ajuste no backend (aceitar lista).

**Operação:** mudar o timeout = `gcloud run services update castro-crm
--update-env-vars TAKEOVER_TIMEOUT_HOURS=N`; pausar = `gcloud scheduler jobs pause
castro-crm-expire-takeovers --location southamerica-east1`.
