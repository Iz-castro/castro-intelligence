## 1. Diagnóstico inicial — por que mensagens não aparecem?

Usuário relatou que histórico de conversas do app celular não estava
aparecendo no CRM após a Fase 3. Mapeei o caminho frontend → backend:

- Frontend (`CrmContext.tsx:872`) sempre passa
  `?conversation_id=${selectedThreadId}` para `/api/wa/messages/{contact_id}`.
- Backend (`main.py:851`) filtra `where conversation_id == X`.
- Mensagens só aparecem se o doc tem `conversation_id` que **bate
  exatamente** com o que o frontend espera.

**5 causas reais encontradas:**

| # | Causa | Local |
|---|---|---|
| 1 | `conversation_id = null` silencioso quando `eff_wa_id` vazio | `database_firestore.py:1233` |
| 2 | `default__{wa_id}` sintético quando `_resolve_webhook_channel` retorna None | `database_firestore.py:545` |
| 3 | Nono dígito BR — contato achado por variante mantém `wa_id` antigo (12-dig sem 9) → conversation_id divergente | `database_firestore.py:733` |
| 4 | `_process_history` direção quebrada — `is_outbound = (msg_from == business_phone)` sem normalização | `webhook.py:902` |
| 5 | `get_wa_conversation` legado mistura threads de canais distintos | `database_firestore.py:1306` |

## 2. Fixes aplicados (commits do trabalho de hoje)

### 2.1 `_make_conversation_id` falha-loud

[database_firestore.py:545-565](../../database_firestore.py#L545-L565) — agora
levanta `ConversationIdError` quando `channel_id` ou `wa_id` ausentes.
Removido o fallback `default__{wa_id}` que ficava órfão pro frontend.

### 2.2 `save_wa_message` propaga ConversationIdError

[database_firestore.py:1244-1262](../../database_firestore.py#L1244-L1262) —
em vez de salvar `conversation_id=None` silenciosamente, levanta exception
e o caller (webhook) é responsável por enfileirar em
`pending_webhook_events`. System messages (transferências, com
`direction='system'`) seguem aceitando null.

### 2.3 `upsert_wa_contact` canoniza wa_id

[database_firestore.py:756-775](../../database_firestore.py#L756-L775) —
quando acha contato via `_find_contact_by_wa_id_any_variant` mas o
`wa_id` armazenado está em forma sem 9 (12-dig), migra pro 13-dig com
9 e atualiza `phone_formatted`. Reflete no dict local antes de
`_maybe_upsert_conversation_for_existing_contact` pra propagar pra
`wa_conversations`.

### 2.4 `_process_history` normaliza phones

[webhook.py:874-893](../../webhook.py#L874-L893) — `business_phone`,
`msg_from`, `msg_to` passam por `normalize_br_phone` antes da comparação
`is_outbound`. Antes: histórico antigo com 12-dig contra business_phone
13-dig fazia tudo virar inbound (ou tudo outbound).

### 2.5 `get_wa_conversation` aceita conversation_id opcional

[database_firestore.py:1320-1333](../../database_firestore.py#L1320-L1333) —
preserva isolamento de canais no fallback legado. Endpoint
`/api/wa/messages/{contact_id}` simplificado pra usar a função única.

### 2.6 `operator_id` populado em smb_message_echoes e history outbound

[webhook.py:746-750](../../webhook.py#L746-L750) e
[webhook.py:1009-1027](../../webhook.py#L1009-L1027) — echo do celular
estava salvo sem `operator_id`, e o frontend
([formatting.ts:35](../../frontend/src/utils/formatting.ts#L35)) usa
esse campo pra decidir entre "Bot" / "Equipe" / nome do operador. Agora
mensagens do app celular gravam `operator_id = channel_owner_user_id`
(o humano dono do número). Frontend para de rotular como "Bot".

## 3. Sistema novo — fila `pending_webhook_events`

Decisão alinhada com Rafa: webhook nunca pode propagar 5xx pra Meta
(senão Meta penaliza endpoint), e nunca pode perder evento. Solução:

### 3.1 `pending_events.py` (módulo novo)

Coleção GLOBAL (fora de `tenants/`) `pending_webhook_events`.
Schema: `{id, received_at, change_field, phone_number_id, reason,
status, attempts, last_attempt_at, last_error, payload}`.

Funções:
- `enqueue_pending_event(payload, change_field, phone_number_id, reason)`
- `list_pending_events(status, limit)`
- `get_pending_event(event_id)`
- `mark_event_attempt(event_id, success, error)`
- `mark_event_failed(event_id, error)`
- `delete_pending_event(event_id)`
- `count_pending()`

### 3.2 Webhook entrypoint resiliente

[webhook.py:233-294](../../webhook.py#L233-L294) — `process_webhook_payload`
envolve tudo em try/except top-level. Em qualquer exception, enfileira
o payload completo com `reason="unhandled_exception:..."` e retorna sem
propagar.

`_resolve_webhook_channel` agora retorna `(channel, reason)` em vez de
fazer fallback silencioso. O inner enfileira changes individuais quando
o canal não resolve em fields que dependem dele
(`_CHANNEL_DEPENDENT_FIELDS = {messages, smb_message_echoes, history}`).

### 3.3 4 endpoints admin

Em `main.py` após o bloco de canais:

- `GET /api/admin/pending-webhook-events?status=pending&limit=N`
- `POST /api/admin/pending-webhook-events/{id}/retry` — re-roda
  `process_webhook_payload` (idempotente via `wa_message_id`)
- `POST /api/admin/pending-webhook-events/{id}/dismiss` — marca como
  failed sem retentar
- `DELETE /api/admin/pending-webhook-events/{id}`

UI da fila para admin **fica pendente** — endpoints prontos pra
consumir quando frente de UI rolar.

## 12. Bug de ordenação descoberto + fixado

Frontend ordenava mensagens por `created_at` (momento de salvar).
Mensagens do history acabaram de chegar com `created_at = ~03:31`
mas `timestamp_wa = data real`. Resultado: timeline invertida — a
fala "ola mundo, mensagem de teste" de 02:30 UTC apareceria DEPOIS
das mensagens de janeiro.

Pior: backend `get_wa_conversation` faz `.order_by("created_at",
"desc").limit(N)` — paginação retornaria N mensagens do history
primeiro, escondendo as de hoje até scroll profundo.

### 12.1 Fix em 3 lugares

- [database_firestore.py:1320](../../database_firestore.py#L1320) —
  backend `get_wa_conversation` ordena por `timestamp_wa DESC`
- [CrmContext.tsx:837](../../frontend/src/context/CrmContext.tsx#L837) —
  frontend snapshot Firestore ordena por `timestamp_wa`
- [CrmContext.tsx:842](../../frontend/src/context/CrmContext.tsx#L842) —
  sort em JS usa `timestamp_wa || created_at` (fallback pra system
  messages legadas sem timestamp_wa)

### 12.2 Índices Firestore atualizados

[firestore.indexes.json](../../firestore.indexes.json) — substituído
`wa_messages: contact_id+created_at` e `wa_messages: conversation_id
+created_at` por `+timestamp_wa DESC`. Deploy:

```
firebase deploy --only firestore:indexes --force
```

### 13.1 Fix aplicado

[webhook.py:836-908](../../webhook.py) — `_process_smb_app_state_sync`

## 15. Aprendizados da sessão (anti-padrões pra evitar)

1. **Eu afirmei várias vezes que history era assíncrono "Meta entrega
   quando quiser, até 24h"**, sem ler a doc. A doc é clara: precisa
   chamar `POST /smb_app_data` ativamente. Lição: ler doc oficial
   antes de afirmar comportamento de API externa, especialmente em
   "fluxos de sincronização" que invariavelmente são triggers
   explícitos.

2. **Fix de `_make_conversation_id` falha-loud sem channel_id causou
   regressão silenciosa.** Quando você endurece um contrato, todos os
   callers que dependiam do comportamento permissivo quebram. Lição:
   antes de levantar exception em função core, grep todos os callers
   pra entender quem passa `None` e ajustar cada um.

3. **Trocar coluna de `order_by` requer índice novo + invalida o
   antigo.** Janela entre criar índice novo e remover índice antigo é
   crítica — se Cloud Run roda código velho com índice novo (ou
   código novo com índice velho), queries quebram. Lição: deploy de
   índice + código deveriam ser atomizados, ou pelo menos sequenciados
   com índice antes do código.
