## 1. Fase 4 — Ciclo de vida do Atendimento (commit `ea2cbbc`)

Base do PO em §3.5 do plano: o Atendimento tem `aberto`/`fechado_*`, fecha
sozinho por inatividade, reabre na próxima mensagem.

**Backend:**
- Novo campo `attendance_status` em `wa_conversations` (`aberto` /
  `fechado_inatividade` / `fechado_manual`; ausente = aberto).
- `upsert_wa_conversation` nasce "aberto" e **reabre em qualquer mensagem**
  (inbound ou outbound).
- `close_stale_attendances(horas)` (espelha `expire_stale_takeovers`): fecha
  apenas atendimentos **atribuídos** ociosos > `ATTENDANCE_AUTOCLOSE_HOURS`
  (decisão do PO: fila/bot não fecham — não são atendimentos em curso).
- Cron `*/30` existente (`castro-crm-expire-takeovers`) passa a rodar
  takeover-expire **E** auto-close na mesma passada — **sem job novo**.
- `POST /api/wa/conversation/{id}/set-attendance` (dono / admin / sup) p/
  fechar/reabrir manual; fechar manual zera takeover.

**Frontend:**
- `normalizeConversation` + `types.ts` mapeiam `attendance_status`.
- Badge **🔒 fechado** na faixa de contexto.
- Item **"Fechar/Reabrir atendimento"** no menu ⋮ do header (label inverte
  conforme estado).

**Decisões registradas (do PO):**
- Auto-close **só atribuídos** (não fila/bot).
- UI v1: badge + thread continua na lista (sem aba "Fechados" — refinamento
  futuro).
- Fechar manual **zera o takeover** (encerra qualquer sessão temporária).

**Quantificação prévia (read-only):** das 98 conversas em prod, **97 atribuídas**
e **90 com `last_message_at` > 24h** → 90 fechariam de uma só vez na 1ª
passada do cron pós-deploy. Comportamento correto (são threads de teste
antigas, ociosas), one-time; reabrem em qualquer nova mensagem.

## 4. Fase 5A — Protocolo de Atendimento (commit `15b4c7a`, rev `castro-crm-00124-298`)

Spec do PO (§3.6 + spec entregue na sessão):
> 1 Dia = 1 Protocolo por Lead. Geração silenciosa no 1º inbound; envio ao
> cliente SÓ no fechamento como "recibo"; semáforo `protocolo_informado`
> bloqueia reenvio no retorno-zumbi do mesmo dia.

**Decisão arquitetural:** nova coleção tenant-scoped (per spec — "A coleção
Atendimentos deve desvincular-se da de Leads"), em vez de bloar campo no
contato. Permite busca/auditoria por protocolo com histórico.

### 4.1 Backend — `database_firestore.py`

- Nova coleção `attendances_daily/{YYYYMMDD-{contact_id}-{SETOR}}` (TZ Brasil
  -3 fixo; SETOR = 3 letras ASCII upper do nome do departamento, fallback
  `GERAL`). Doc: `id`, `contact_id`, `date`, `setor`, `criado_em`,
  `ultima_interacao`, `status`, `protocolo_informado`, `fechado_em`,
  `fechado_por_user_id`.
- Helpers:
  - `_today_br_str()`, `_setor_code()`.
  - `ensure_daily_attendance(contact_id, setor=None)` — get-or-create + reopen
    preservando `protocolo_informado` (regra do zumbi).
  - `get_daily_attendance`, `close_daily_attendance`,
    `mark_protocol_informed`, `get_current_protocol_id`,
    `get_messages_by_protocol`.
- `save_wa_message` denormaliza `protocol_id` em cada mensagem:
  - **inbound** → chama `ensure_daily_attendance` (cria/reabre).
  - **outbound/internal/system** → `get_current_protocol_id` (só lê).
- `close_stale_attendances` agora retorna também `channel_id` (precisa pro
  envio do protocolo no cron).

### 4.2 Backend — `main.py`

- `_close_daily_and_send_protocol(contact, conv, channel, current_user, close_status)`
  (async): no fechamento, se `protocolo_informado=false` E `last_inbound` ≤24h:
  - Envia `"Seu protocolo de hoje é {id}. Agradecemos pela confiança em nossa empresa."` à Meta.
  - Salva como `wa_messages` outbound (`sender_user_id` = quem fechou).
  - Marca `protocolo_informado=true`.
  - Atualiza `attendances_daily.status` para `fechado_{manual|inatividade}` +
    `fechado_em` / `fechado_por_user_id`.
  - Fora de 24h: fecha sem enviar (mesma regra do Modo 3 — sem template
    aprovado).
- **Hook em `set-attendance` manual** (Fase 4 endpoint): chama o helper ao
  fechar; ao reabrir, volta o Atendimento diário pra `aberto` preservando o
  semáforo.
- **Hook no cron `expire-takeovers`**: pra cada thread auto-fechada, tenta
  enviar protocolo. **Idempotente entre threads do mesmo Lead/dia** via a
  flag (Lead com 3 threads coex fechando simultaneamente → 1 envio só).
- `GET /api/admin/protocol/{protocol_id}` (admin/sup) → retorna Atendimento +
  timeline de mensagens do dia (denorm `protocol_id` permite consulta direta
  por igualdade).
- **`/api/wa/assume/{contact_id}` NÃO gera mais protocolo** (mudança de
  comportamento alinhada à spec — só o webhook na 1ª inbound do dia gera).
  Espelho `wa_contacts.attendance_protocol` mantido para back-compat com o
  "Copiar protocolo" do menu ⋮.

### 4.3 Frontend

- `types.ts`: `ProtocolAtendimento`, `ProtocolSearchResult`.
- `CrmContext`: `loadProtocol(protocolId)` (admin/sup).
- `App.tsx`:
  - Faixa de contexto mostra **📄 {protocol_id}** do dia.
  - Novo card admin **"Buscar protocolo"** no detail-panel (input + timeline
    com bordas coloridas por direction: inbound azul, outbound verde,
    internal amarelo, system cinza).

### 4.4 Salvaguardas

- O helper só envia se o pid está no formato **novo** (`YYYYMMDD-...`).
  Threads antigos (formato `ATD-YYYYMMDDHHMMSS-id5`) **não recebem spam** no
  próximo cron — só Leads que tiverem inbound a partir do deploy entram no
  fluxo novo.
- Reabertura por nova mensagem **preserva** `protocolo_informado=true` — o
  cliente não recebe múltiplos "Seu protocolo de hoje é..." numa mesma data.

### 4.5 Eyeball (4 cenários — validado por Rafa)

1. **Geração silenciosa:** novo inbound → faixa mostra `📄 20260528-{cid}-SETOR`. Cliente não recebeu nada.
2. **Fechar manual:** ⋮ → "Fechar atendimento" → cliente recebe a frase do protocolo (≤24h).
3. **Retorno-zumbi:** Lead responde após fechado → reabre; fechar de novo **não reenvia**.
4. **Buscar protocolo:** detail-panel → card "Buscar protocolo" → cola o id → vê atendimento + timeline.

## 8. Aprendizados / pontos de atenção

- **Auto-close + protocolo são gradiente:** o cron `*/30` + threshold 6h
  + envio do protocolo no fechamento criam um fluxo automatizado bonito —
  o operador não precisa "lembrar" de mandar protocolo, o sistema vira o
  carimbo do dia. Mas é também superfície de envio à Meta sob controle
  do cron — vale monitorar `audit_log` por `ATTENDANCE_AUTO_CLOSE` e o
  rate de protocolos enviados pra detectar surto anômalo.
- **Salvaguarda do formato pid (`YYYYMMDD-...`)** evitou um problema clássico
  de migração: 90 threads ociosas com protocolo antigo (`ATD-...`) seriam
  todas elegíveis pro envio na primeira passada do cron pós-deploy. O guard
  no helper bloqueia → só threads que receberam inbound após o deploy
  entram no fluxo novo. Limpeza orgânica.
- **TZ Brasil hardcoded (-3 fixo)** é OK porque BR não tem DST desde 2019.
  Quando o produto for além do BR, parametrizar por tenant.
- **`assume` não gera mais protocolo:** mudança sutil de comportamento mas
  alinhada à spec. Operadores que "assumiam para gerar protocolo" agora
  precisam de inbound do cliente (ou de outro disparo) pra o protocolo
  existir. Pode aparecer em algum fluxo se o operador-assume era usado
  como hack — fica registrado no doc do dia.
