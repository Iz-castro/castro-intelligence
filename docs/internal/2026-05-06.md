### 3.4. Firestore rules estritas em staging (WIP, não commitado)

**Objetivo:** substituir as rules permissivas (`emailAllowed()` libera
qualquer email autorizado em qualquer subcoleção do tenant) por rules
**tenant-scoped via custom claim `tenant_id`** no JWT, aplicando ACL
granular por role/department dentro do tenant. Pré-requisito do
cutover prod (§ 2.9 do plano).

**Estado ao parar:**
- Arquivo WIP preservado em
  [`docs/internal/firestore-rules-staging-strict.wip`](firestore-rules-staging-strict.wip)
  (220 linhas).
- Firebase voltou ao estado permissivo (deployed após `git checkout
  firestore.rules`) pra não bloquear uso humano de staging.
- `auth.py` ganhou fix em `_resolve_tenant_id`: agora usa
  `get_tenant_context()` como fallback quando claim ausente E doc do
  user não tem `tenant_id` (caso comum hoje porque user mora dentro
  de `tenants/hubloc/users/`, redundante com path).

**Bug encontrado e parcialmente diagnosticado:**

1. **Custom claims do rafa estavam vazios** (`custom_claims=None`
   verificado via `auth.get_user_by_email().custom_claims`).
   `bootstrap_admin_user` chama `set_tenant_claims(firebase_uid, ...)`
   mas só se `firebase_uid` está populado no doc do user. Pra users
   provisionados via Firebase SSO antes do bootstrap, esse campo pode
   estar vazio ou desatualizado.

   **Mitigação aplicada manualmente:**
   ```python
   auth.set_custom_user_claims(
       'znkzvZTl2kZ4gmg95pHjBLElEjS2',
       {'tenant_id': 'hubloc', 'role': 'admin'},
   )
   ```

2. **Mesmo após setar claims + logout/login + janela anônima**, o
   snapshot de `wa_messages` continua falhando com `Missing or
   insufficient permissions`. O snapshot de `wa_conversations` (mesma
   chain de regra `canSeeContactScoped` que internamente checa
   `ownsTenant`) retornava 3 conversas inicialmente, mas ao tentar abrir
   uma conversa o snapshot de mensagens é negado.

   Hipóteses ainda não validadas:
   - Custom claim setado server-side (confirmado via Admin SDK)
     mas **não estava no JWT** que o frontend mandou pra Firestore.
     Possível causa: client SDK do Firebase Auth tem cache local do
     ID token que persiste mesmo após `getIdToken(true)` (algo no
     IndexedDB do navegador). Janela anônima descartaria isso, mas o
     erro persistiu — sugerindo que o issue é OUTRO.
   - **Query com `where + orderBy + limit` em wa_messages exige rule
     "fully constrained"**: rules avaliam queries pra TODOS os docs
     possíveis, não só pra os que satisfazem o filter. Se a rule
     depende de `request.auth.token.tenant_id` (path-static, não
     resource.data), em teoria deveria passar — mas pode haver
     interação com o filter `conversation_id` que não vi.
   - **Bundle JS cached**: o frontend pode estar lendo paths flat
     antigos (`castro_crm_staging_wa_messages`) em vez de tenant-scoped
     em algum codepath. `/api/session` retornou os paths corretos
     (validado), mas pode haver fallback no client.

**Para retomar:**

1. **Reproduzir ambiente limpo:** abrir janela anônima, login,
   inspector aberto. Antes de clicar em conversa, **rodar no console**
   pra ver o JWT real:
   ```js
   firebase.auth().currentUser.getIdTokenResult(true).then(r => {
     console.log('claims:', JSON.stringify(r.claims));
     console.log('aud:', r.authTime, 'exp:', r.expirationTime);
   })
   ```
   Confirma se `tenant_id`/`role` aparecem no JWT.

2. **Se claims OK mas snapshot ainda nega:** simular a query no
   Firebase Console → Firestore → Rules Playground:
   - Operation: `list` (não `get`)
   - Path: `castro_crm_staging_tenants/hubloc/wa_messages/anyMessageId`
   - Authenticated: yes, custom claims `{tenant_id: hubloc, role: admin}`
   - Query: `where conversation_id == ... orderBy created_at desc limit 50`
   Resultado mostra exata linha da rule que nega.

3. **Se claims faltando no JWT mesmo após force-refresh:** investigar
   o lifecycle do Firebase JS SDK. Possivelmente bug em
   `getIdTokenResult(true)` que ignora forceRefresh em certas
   condições (versão do SDK, providers). Pode ser necessário
   `signOut()` + `signInWithPopup()` pra forçar JWT novo do server.

4. **Backup option:** restaurar rules estritas via:
   ```powershell
   cp docs/internal/firestore-rules-staging-strict.wip firestore.rules
   firebase deploy --only firestore:rules --project=project-26fb9c99-8ee9-4179-aef
   ```

**Não influencia App Review pendente** — Meta App Review valida o

Pode-se manter estado permissivo em staging até a investigação seguir.
