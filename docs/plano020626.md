# 📄 Documentação de Arquitetura: Fase 2 - Escalonamento SaaS

## 📌 Escopo do Módulo
Implementação da camada de segurança, controle de acesso e isolamento de dados do sistema CRM para operação em modelo SaaS Multi-tenant. 

---

## 4. Matriz de Permissões (RBAC) e Painel Administrativo
Substituição da lógica estática de validação de papéis no código por Perfis de Acesso (RBAC) dinâmicos, preparando o sistema para a autonomia dos administradores de cada empresa locatária (Tenant).

### 4.1. Estrutura de Dados (Firestore)
* **Localização:** Os perfis não são globais. Eles residem em uma subcoleção dentro de cada Tenant: `castro_crm_tenants/{tenant_id}/perfis_acesso`.
* **Desacoplamento:** O documento individual do usuário (operador) não carrega uma árvore de permissões, apenas uma referência direta ao perfil:
```json
  {
    "user_id": "op_sac_01",
    "nome": "Maria",
    "perfil_acesso_id": "perfil_sac_integrado"
  }
  ```

### 4.2. Interface Administrativa (Master-Detail)
* **Layout:** Navegação no padrão "WhatsApp Web".
    * *Painel Esquerdo (Mestre):* Lista de cartões dos perfis de acesso existentes na empresa e botão para criação de novos perfis.
    * *Painel Direito (Detalhe):* Formulário de edição composto exclusivamente por *Toggle Switches* (chaves booleanas) para evitar confusão cognitiva.
* **Agrupamento Lógico das Regras:**
    * *Visibilidade:* Próprios leads, leads do setor, leads de todos os setores.
    * *Ações:* Assumir conversas (Takeover), enviar notas internas, transferir leads.
    * *Gerenciamento:* Acesso a relatórios, exportação de contatos.

### 4.3. Proteção Arquitetural (Lock)
* O documento `perfil_admin` base de cada tenant recebe uma flag nativa: `is_system_locked: true`.
* O front-end (React) lê essa flag e **desabilita** a edição dos toggles críticos e a exclusão deste perfil específico. Isso previne que o administrador da locadora retire seus próprios acessos por acidente (autossabotagem).

## 5. Arquitetura Multi-Tenant e Super Admin (Compliance LGPD)
Isolamento estrutural absoluto entre a gestão das empresas clientes (ex: locadora de máquinas) e a gestão global do SaaS (Castro Intelligence).

### 5.1. Separação de Serviços e Infraestrutura
* **Serviço CRM (Cloud Run A - O Operacional):**
    * Lida com webhooks da Meta, front-end do cliente e IA de resumo.
    * Escopo confinado: Regras de segurança rigorosas garantem que o serviço só leia e escreva dados dentro do caminho `castro_crm_tenants/{tenant_id_da_requisicao}`. Cego para o resto do banco.
* **Serviço Super Admin (Cloud Run B - O Provisionador):**
    * Aplicação web completamente separada.
    * Utiliza Firebase Admin SDK com privilégios totais de sistema.
    * Responsável exclusivo pela criação de novos Tenants, faturamento e injeção da *seed* de Perfis de Acesso (RBAC) durante o onboarding de uma nova empresa.

### 5.2. Gestão de Identidade do Super Admin (Modelo Híbrido)
A validação de quem é o dono do SaaS utiliza a abordagem de maior performance e segurança no Firebase:

* **Custom Claims (O "Fast-path"):** A variável `super_admin: true` é injetada no JWT (token) via Firebase Auth. Utilizada para liberar acessos amplos em *Security Rules* sem gerar custos de leitura (`reads`) no Firestore.
* **Firestore Base (Source of Truth):** Um documento inviolável em `super_admins/{uid}`. É utilizado pelo back-end (Cloud Run B) para validação profunda em rotas sensíveis (escrita, leitura cross-tenant e exportação de dados). **O Claim sozinho não autoriza operações nucleares.**

### 5.3. Checklist Rigoroso de Segurança e LGPD
Para evitar o "cenário nuclear" (vazamento de dados pessoais de múltiplos tenants), o serviço Super Admin obedece a três leis:
1. **MFA Obrigatório:** O acesso ao painel do Cloud Run B exige Autenticação de Dois Fatores (TOTP/SMS) habilitada no Firebase Auth. O back-end exige a flag `mfa_enrolled: true` no documento do Super Admin.
2. **Audit Trail Intocável:** Qualquer ação realizada pelo Super Admin (criar tenant, ler logs, alterar permissões) gera uma gravação automática na coleção global `audit_logs_system` contendo: *quem fez*, *quando*, *IP* e o *motivo da operação*.
3. **Revogação Instantânea (Kill Switch):** Em caso de comprometimento, a exclusão do documento `super_admins/{uid}` somada ao comando `admin.auth().revokeRefreshTokens(uid)` invalida instantaneamente a sessão ativa, anulando o acesso antes que o TTL de 1 hora do token expire.
